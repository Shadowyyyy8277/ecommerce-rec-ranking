# 电商推荐召回与 CTR 排序系统项目报告

## 1. 项目概述

本项目是一个面向电商推荐场景的端到端机器学习实践项目，目标是构建一个从用户行为数据处理、多路召回、排序建模、离线评估、实验管理到在线推理服务的完整推荐系统流程。

项目使用模拟电商用户行为数据构建离线实验环境，不涉及任何真实业务数据。项目重点不在于追求线上业务指标，而在于复现工业推荐系统中的核心技术链路，并展示推荐算法、特征工程、模型评估和工程化部署能力。

完整流程如下：

```text
用户行为数据
    ↓
数据清洗与时间切分
    ↓
特征工程
    ↓
多路召回
    ↓
CTR 排序模型训练
    ↓
模型对比与离线评估
    ↓
模型注册与实验追踪
    ↓
FastAPI 在线推理服务
    ↓
Streamlit 推荐展示 Demo
```

本项目实现了 Popular Recall、ItemCF、Item2Vec 等召回方式，并对 LR、LightGBM、DeepFM 三类 CTR 排序模型进行了对比实验。最终根据验证集效果选择 LightGBM 作为当前在线推理模型。

---

## 2. 项目目标

推荐系统通常可以拆分为召回、排序、重排和展示等阶段。本项目聚焦于推荐系统中的两个核心环节：

- **候选商品召回**：从大量商品中筛选出可能与用户兴趣相关的候选集；
- **CTR 排序建模**：对候选商品进行点击或转化倾向预测，并按照模型分数生成 Top-K 推荐结果。

项目主要目标包括：

- 构建一个可运行的端到端推荐系统实验流程；
- 实现多种召回策略，并将召回结果融合为候选商品集合；
- 使用 LR、LightGBM、DeepFM 对候选商品进行排序建模；
- 使用 AUC、LogLoss、Precision@K、Recall@K、NDCG@K、HitRate@K 等指标进行离线评估；
- 使用 MLflow 记录模型实验过程和关键指标；
- 使用模型注册文件保存当前最佳模型；
- 使用 FastAPI 提供在线推荐接口；
- 使用 Streamlit 构建可视化推荐展示页面。

## 4. 数据说明

本项目使用模拟电商用户行为数据，数据中包含用户、商品、类目、行为类型、价格、时间等字段。数据主要用于模拟电商场景中的用户浏览、点击、购买等行为，并构造推荐排序任务。

为了避免模型学习到不合理的信息泄漏，训练过程中没有直接将 `label`、`behavior_type`、`timestamp` 等目标相关或强泄漏字段直接作为模型输入特征，而是通过历史统计、用户偏好、商品热度、类目偏好等方式构造特征。

数据按照时间顺序划分为：

```text
Train
Valid
Test
```

这种划分方式更接近推荐系统中的真实离线实验设定，可以减少随机切分带来的时间泄漏问题。模型只能基于历史数据学习用户偏好，并在后续时间段上验证推荐效果。

## 6. 推荐流程设计

### 6.1 数据处理

数据处理阶段主要完成以下工作：

- 读取模拟用户行为数据；
- 按时间顺序划分 train、valid、test；
- 生成训练排序模型所需的样本；
- 保存处理后的数据文件；
- 为后续召回、特征工程、模型训练提供统一输入。

时间切分方式能够更好地模拟真实推荐场景中的训练与预测过程：模型只能使用过去的行为数据去预测未来的用户兴趣。

---

### 6.2 多路召回

召回阶段的目标是从商品全集中为每个用户筛选出一批候选商品，降低后续排序模型的计算压力。

本项目实现了三类召回策略：

#### 1. Popular Recall

Popular Recall 根据商品在训练数据中的整体热度进行召回。它实现简单、稳定性强，适合作为兜底策略。

优点：

- 实现简单；
- 对冷启动用户友好；
- 可以作为模型不可用时的 fallback。

局限：

- 个性化程度较弱；
- 容易偏向热门商品；
- 对长尾商品覆盖不足。

#### 2. ItemCF Recall

ItemCF 基于用户历史交互行为构造商品之间的相似度。如果用户历史上喜欢某些商品，则召回与这些商品相似的其他商品。

优点：

- 能够利用用户历史行为；
- 具有一定个性化能力；
- 适合推荐与用户历史兴趣相似的商品。

局限：

- 对稀疏数据比较敏感；
- 对冷启动商品支持有限；
- 相似度计算在大规模场景下需要进一步优化。

#### 3. Item2Vec Recall

Item2Vec 将用户行为序列中的商品视为上下文，学习商品向量表示，并基于向量相似度进行召回。

优点：

- 能够捕捉商品之间的隐含语义关系；
- 相比传统共现统计，可以表达更复杂的商品相似性；
- 适合行为序列较丰富的推荐场景。

局限：

- 对训练数据规模有要求；
- 需要合理设置窗口大小、向量维度等参数；
- 在小规模模拟数据上效果可能不如真实业务数据明显。

多路召回结果最终会进行合并，形成排序模型的候选商品集合。

---

### 6.3 特征工程

排序模型需要使用用户、商品、类目和召回相关特征来预测候选商品的点击或转化倾向。

本项目的特征工程主要包括：

- 用户历史行为统计；
- 用户类目偏好特征；
- 商品历史热度特征；
- 商品价格相关特征；
- 类目统计特征；
- 召回分数与召回类型特征；
- 用户与商品之间的交叉特征。

特征工程的核心目标是将原始行为数据转化为模型可学习的数值与类别特征，使排序模型能够同时利用用户偏好、商品质量和召回信息。

在特征构造过程中，项目尽量避免直接使用目标相关字段作为输入，从而降低目标泄漏风险，使模型评估结果更可信。

---

### 6.4 CTR 排序模型

本项目对比了三类 CTR 排序模型：

#### 1. Logistic Regression

LR 是推荐排序中的经典线性基线模型，具有训练速度快、可解释性强、部署简单等特点。

在本项目中，LR 主要作为排序任务的 baseline，用于验证特征工程和标签构造是否合理。

#### 2. LightGBM

LightGBM 是基于梯度提升树的排序模型，适合处理表格型特征，能够自动学习非线性特征组合。

在本项目中，LightGBM 在验证集上取得了最好的 AUC 和 LogLoss，因此被选为当前在线推理模型。

#### 3. DeepFM

DeepFM 结合了因子分解机和深度神经网络，能够同时学习低阶和高阶特征交互，常用于 CTR 预估任务。

在本项目中，DeepFM 被用于补充深度排序模型实验。由于当前数据规模较小，DeepFM 的效果弱于 LightGBM，这也符合小规模表格数据场景下树模型通常更稳定的经验。

## 8. 模型效果

### 8.1 验证集模型对比

| Model | Valid AUC | Valid LogLoss |
|---|---:|---:|
| LR | 0.5666 | 0.3955 |
| LightGBM | 0.5784 | 0.3917 |
| DeepFM | 0.5417 | 0.4200 |

从验证集结果看，LightGBM 的 AUC 最高，LogLoss 最低，整体表现优于 LR 和 DeepFM。因此本项目选择 LightGBM 作为最终排序模型。

### 8.2 测试集结果

|---|---:|

测试集结果说明，LightGBM 在独立测试集上保持了与验证集接近的表现，模型没有出现明显的验证集过拟合现象。

### 8.3 Top-K 推荐评估

| Metric | Value |
|---|---:|
| HitRate@5 | 0.0379 |
| HitRate@10 | 0.0966 |
| HitRate@20 | 0.2034 |
| NDCG@20 | 0.0578 |

Top-K 指标用于评估推荐列表的整体命中情况和排序质量。其中 HitRate@20 表示在推荐前 20 个商品中命中用户目标行为的比例，NDCG@20 则考虑了命中商品在推荐列表中的排序位置。

### 9.1 FastAPI 推荐接口

本项目使用 FastAPI 提供在线推荐接口。

主要接口包括：

```text
GET /health
POST /recommend
```

`/health` 用于检查服务状态和模型是否可用。

`/recommend` 接收用户 ID 和 Top-K 数量，返回推荐商品列表、排序分数和简短推荐理由。

请求示例：

```json
{
  "user_id": "u_000001",
  "top_k": 10
}
```

响应示例：

```json
{
  "user_id": "u_000001",
  "recommendations": [
    {
      "item_id": "i_000628",
      "score": 0.2822,
      "reason": "LightGBM predicted the highest CTR among recalled candidates."
    }
  ]
}
```

## 10. 工程化设计

本项目不仅包含模型训练，还设计了完整的工程化流程。

### 10.1 配置化管理

项目通过配置文件统一管理路径、训练参数、服务参数等内容，减少硬编码，提高可维护性。

### 10.2 脚本化运行

数据处理、召回、模型训练、评估等步骤均可以通过脚本运行，便于复现实验流程。

### 10.3 模型注册

训练完成后，项目会根据验证集指标选择当前最佳模型，并写入模型注册文件。在线服务读取该文件后自动加载对应模型。

### 10.4 Fallback 机制

当模型或召回结果不可用时，系统会回退到热门商品推荐，保证服务接口仍然可用。

这种设计可以提升 Demo 稳定性，也体现了线上推荐服务中常见的兜底思路。

### 10.5 在线推理服务

FastAPI 服务负责提供推荐接口，Streamlit 页面负责展示推荐结果。两者结合后，可以完整展示从模型训练到在线推理的闭环。

## 12. 项目局限性

本项目仍然存在一些局限：

- 当前数据为模拟数据，无法完全反映真实电商场景中的长尾分布、冷启动、多目标优化和实时反馈问题；
- DeepFM 在当前小规模数据下表现弱于 LightGBM，后续可以在更大规模样本上进一步调参和训练；
- 当前推荐理由主要用于 Demo 展示，真实业务中需要结合用户画像、商品知识和可解释推荐方法进行更细粒度设计；
- 当前服务是本地单机 Demo，尚未接入 Redis、Kafka、特征服务、A/B 实验平台和线上监控系统；
- 当前排序目标较单一，后续可以扩展为点击率、转化率、GMV、停留时长等多目标排序任务。

## 14. 总结

本项目完成了一个从离线实验到在线服务的电商推荐排序系统。项目实现了多路召回、CTR 排序模型训练、模型效果对比、Top-K 推荐评估、MLflow 实验管理、模型注册、FastAPI 在线推理和 Streamlit 可视化展示。

在模型效果上，LightGBM 在验证集和测试集上表现最稳定，因此被选为最终排序模型。在工程实现上，项目通过配置化、脚本化、模型注册和 fallback 机制，提高了实验复现性和服务稳定性。

整体来看，本项目展示了一个推荐系统项目从算法设计、特征工程、模型训练、离线评估到工程化部署的完整闭环。
